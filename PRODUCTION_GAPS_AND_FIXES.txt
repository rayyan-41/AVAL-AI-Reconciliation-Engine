ISSUE 01 — SINGLE JDBC CONNECTION SHARED ACROSS CONCURRENT THREADS
Severity  : BLOCKING
Files     : src/main/java/aval/persistence/DataStore.java
            src/main/java/aval/Main.java
            pom.xml
================================================================================

PROBLEM
-------
DataStore holds exactly one java.sql.Connection object:

    private Connection connection;
    public DataStore(Connection connection) { this.connection = connection; }

Every method in DataStore uses this single connection directly. JDBC Connection
objects are NOT thread-safe. The integration plan requires multiple JavaFX
Task<T> threads running concurrently:
  - Ledger ingestion Task writes to standardized_ledger
  - Bank ingestion Task writes to standardized_bank
  - Auth Task reads from system_user

When two Tasks call DataStore at the same time, you get:
  - "Connection is closed" SQLExceptions
  - Corrupted ResultSet reads (one thread's cursor advanced by another)
  - Silent data loss

This is intermittent and hard to reproduce in testing, which makes it dangerous.

FIX — Replace the single Connection with HikariCP connection pool
-----------------------------------------------------------------

Step 1. Add HikariCP to pom.xml (inside <dependencies>):

    <dependency>
        <groupId>com.zaxxer</groupId>
        <artifactId>HikariCP</artifactId>
        <version>5.1.0</version>
    </dependency>

Step 2. Replace DataStore constructor and field:

    // REMOVE this:
    private Connection connection;
    public DataStore(Connection connection) { this.connection = connection; }

    // ADD this:
    import com.zaxxer.hikari.HikariConfig;
    import com.zaxxer.hikari.HikariDataSource;
    import javax.sql.DataSource;

    private final DataSource dataSource;

    public DataStore(DataSource dataSource) {
        this.dataSource = dataSource;
    }

Step 3. In every DataStore method, replace:

    // BEFORE (unsafe — uses shared connection):
    PreparedStatement ps = connection.prepareStatement(sql);

    // AFTER (safe — borrows a connection from the pool, returns it on close):
    try (Connection conn = dataSource.getConnection();
         PreparedStatement ps = conn.prepareStatement(sql)) {
        // ... rest of method unchanged
    }

    This pattern works because HikariDataSource.getConnection() returns a
    pooled connection, and the try-with-resources closes (returns) it when done.
    Each Task gets its own connection. No sharing, no races.

Step 4. Change Main.java service wiring:

    // REMOVE:
    Connection conn = DriverManager.getConnection(url, user, pass);
    DataStore dataStore = new DataStore(conn);

    // ADD:
    HikariConfig config = new HikariConfig();
    config.setJdbcUrl("jdbc:postgresql://localhost:5432/aval_db");
    config.setUsername("aval_user");
    config.setPassword("aval_password");
    config.setMaximumPoolSize(10);
    config.setMinimumIdle(2);
    config.setConnectionTimeout(30000);
    config.setIdleTimeout(600000);
    HikariDataSource hikariDataSource = new HikariDataSource(config);
    DataStore dataStore = new DataStore(hikariDataSource);

    // Add shutdown hook so the pool closes cleanly when the app exits:
    Runtime.getRuntime().addShutdownHook(new Thread(hikariDataSource::close));

VERIFICATION
------------
After this change, start the app and simultaneously:
1. Load a ledger file (triggers standardize() Task)
2. While it is running, load a bank PDF (triggers another standardize() Task)
Both should complete without any SQLException in the console.

ISSUE 02 — NO PASSWORD VERIFICATION (AUTH IS DECORATIVE)
Severity  : BLOCKING
Files     : src/main/java/aval/ui/controller/AuthController.java
            src/main/java/aval/persistence/DataStore.java
            db-init/01-init.sql
================================================================================

PROBLEM
-------
The system_user table has no password column:

    CREATE TABLE system_user (
        user_id UUID PRIMARY KEY,
        username VARCHAR(50) UNIQUE NOT NULL,
        role VARCHAR(20) NOT NULL
    );

AuthController checks only that the passkey field is non-blank. Any non-empty
string is accepted. Knowing a valid username is all that is required to log in.

FIX — Add password_hash column and bcrypt verification
------------------------------------------------------

Step 1. Add password_hash column to the DB schema.
Add this to db-init/01-init.sql (or run it as a migration):

    ALTER TABLE system_user ADD COLUMN password_hash VARCHAR(255) NOT NULL DEFAULT '';

    -- Seed a test user with bcrypt hash of "aval2024" (generated offline):
    INSERT INTO system_user (user_id, username, role, password_hash)
    VALUES (
        gen_random_uuid(),
        'WS-0001-ARYA',
        'ACCOUNTANT',
        '$2a$12$Kix.9A1VRoH0jNZ5vD0WaOivHBKQ3XOhZ2W5XW5CJbE3YHI8SQBKK'
    );
    -- The hash above is bcrypt of "aval2024" with cost 12.
    -- Generate your own hashes using: https://bcrypt-generator.com/

Step 2. Add BCrypt to pom.xml:

    <dependency>
        <groupId>org.mindrot</groupId>
        <artifactId>jbcrypt</artifactId>
        <version>0.4</version>
    </dependency>

Step 3. Add findSystemUserByCredentials() to DataStore.java:

    import org.mindrot.jbcrypt.BCrypt;

    public SystemUser findSystemUserByCredentials(String username, String passkey) {
        String sql = "SELECT user_id, username, role, password_hash " +
                     "FROM system_user WHERE username = ?";
        try (Connection conn = dataSource.getConnection();
             PreparedStatement ps = conn.prepareStatement(sql)) {
            ps.setString(1, username);
            try (ResultSet rs = ps.executeQuery()) {
                if (rs.next()) {
                    String storedHash = rs.getString("password_hash");
                    if (BCrypt.checkpw(passkey, storedHash)) {
                        return new SystemUser(
                            (UUID) rs.getObject("user_id"),
                            rs.getString("username"),
                            UserRole.valueOf(rs.getString("role"))
                        );
                    }
                }
            }
        } catch (SQLException e) {
            System.err.println("findSystemUserByCredentials failed: " + e.getMessage());
        }
        return null; // null = bad credentials
    }

Step 4. Update AuthController.handleAuthenticate():

    @FXML
    private void handleAuthenticate() {
        String username = workspaceIdField.getText().trim();
        String passkey  = passkeyField.getText();

        if (username.isBlank()) {
            workspaceIdField.setStyle(
                "-fx-border-color: transparent transparent #991b1b transparent;");
            return;
        }
        if (passkey.isBlank()) {
            passkeyField.setStyle(
                "-fx-border-color: transparent transparent #991b1b transparent;");
            return;
        }

        DataStore ds = MainUIContext.getInstance().getDataStore();

        Task<SystemUser> authTask = new Task<>() {
            @Override protected SystemUser call() {
                return ds.findSystemUserByCredentials(username, passkey);
            }
        };

        authTask.setOnSucceeded(e -> Platform.runLater(() -> {
            SystemUser user = authTask.getValue();
            if (user != null) {
                MainUIContext.getInstance().setCurrentUser(user);
                navigateTo("Registry.fxml");
            } else {
                // Show error — do NOT say which field is wrong (security)
                workspaceIdField.setStyle(
                    "-fx-border-color: transparent transparent #991b1b transparent;");
                passkeyField.setStyle(
                    "-fx-border-color: transparent transparent #991b1b transparent;");
            }
        }));

        authTask.setOnFailed(e -> Platform.runLater(() -> {
            // DB unavailable — fail CLOSED (see Issue 03)
            workspaceIdField.setStyle(
                "-fx-border-color: transparent transparent #991b1b transparent;");
        }));

        new Thread(authTask).start();
    }

VERIFICATION
------------
- Correct username + correct passkey -> navigates to Registry.
- Correct username + wrong passkey -> stays on Auth, both fields highlighted.
- Unknown username -> stays on Auth, both fields highlighted.
- DB offline -> stays on Auth (fails closed, see Issue 03).

ISSUE 03 — AUTH FALLBACK FAILS OPEN (DB UNAVAILABLE = FREE LOGIN)
Severity  : BLOCKING
Files     : src/main/java/aval/ui/controller/AuthController.java
            src/main/java/aval/Main.java
================================================================================

PROBLEM
-------
The integration plan recommended a dev-mode fallback where, if the DB is
unreachable, a synthetic SystemUser is created and the user is admitted anyway.
This is a security hole. A production machine with a DB connectivity blip would
accept ANY login with no validation.

FIX — Remove the fallback entirely. Fail closed.
------------------------------------------------

In AuthController, the Task.setOnFailed handler must NOT create a synthetic user.
It must show an error and stay on the Auth screen (see Issue 02 fix above — the
setOnFailed handler already does this correctly).

In Main.java, wrap the connection pool creation in a try-catch. If the DB is
unreachable at startup, show a dialog and exit cleanly instead of continuing:

    try {
        HikariDataSource hikariDataSource = new HikariDataSource(config);
        dataStore = new DataStore(hikariDataSource);
    } catch (Exception e) {
        Alert alert = new Alert(Alert.AlertType.ERROR);
        alert.setTitle("Database Unavailable");
        alert.setHeaderText("Cannot connect to AVAL database.");
        alert.setContentText(
            "Ensure Docker Compose is running: docker compose up db\n\n" +
            "Error: " + e.getMessage());
        alert.showAndWait();
        Platform.exit();
        return;
    }

VERIFICATION
------------
Stop the Docker database container. Launch the app. An error dialog should
appear and the application should exit. It must NOT reach the login screen.

ISSUE 04 — AUTO-RECONCILED RECORDS MISSING FROM REPORT (CORRECTNESS BUG)
Severity  : BLOCKING
Files     : src/main/java/aval/ui/controller/ReconController.java
            src/main/java/aval/ui/MainUIContext.java
================================================================================

PROBLEM
-------
When ReconciliationService.runMatching() runs, it correctly creates
ReconciliationRecord objects for every AUTO_RECONCILED hypothesis and saves
them to the database via dataStore.saveReconciliationRecords(autoRecords).

However, runMatching() returns only List<MatchHypothesis>. The auto-records are
never returned to the caller. In ReconController.finishReconciliation(), after
the Task completes, no code exists to put those auto-records into
MainUIContext.reconciledRecords.

Result: ReportController.handleGenerate() calls ctx.getReconciledRecords() and
gets only the manually approved records from ManualCheckController. Every
auto-matched transaction (typically 95%+ of the dataset) is absent from the
generated CSV report. The report is silently, severely incomplete.

FIX — Reconstruct auto-records from the hypothesis list after runMatching()
--------------------------------------------------------------------------

In ReconController, inside the task.setOnSucceeded() block, after splitting
the hypotheses by status, add:

    // Reconstruct ReconciliationRecord objects for all auto-reconciled items.
    // These were saved to the DB inside runMatching(), but were not returned.
    // We recreate them in-memory so the report has the full picture.
    SystemUser systemBot = new SystemUser(
        UUID.randomUUID(),
        "System (Auto-Reconcile)",
        UserRole.ADMIN
    );

    List<ReconciliationRecord> autoRecords = all.stream()
        .filter(h -> h.getStatus() == HypothesisStatus.AUTO_RECONCILED)
        .map(h -> new ReconciliationRecord(h, systemBot))
        .collect(Collectors.toList());

    // Seed MainUIContext with the auto-records so the report starts populated.
    // ManualCheckController will append approved manual records on top of these.
    ctx.setReconciledRecords(new ArrayList<>(autoRecords));

Also add setReconciledRecords() and addReconciledRecord() to MainUIContext:

    private List<ReconciliationRecord> reconciledRecords = new ArrayList<>();

    public List<ReconciliationRecord> getReconciledRecords() {
        return reconciledRecords;
    }

    public void setReconciledRecords(List<ReconciliationRecord> records) {
        this.reconciledRecords = records;
    }

    public synchronized void addReconciledRecord(ReconciliationRecord record) {
        this.reconciledRecords.add(record);
    }
    // Note: addReconciledRecord is synchronized because ManualCheckController
    // calls it from a background Task thread (see Issue 06).

VERIFICATION
------------
After running reconciliation on a dataset of N transactions where M are
auto-matched and K go to manual review, then approving all K manually:
- ctx.getReconciledRecords().size() should equal M + K (approved manual ones).
- The generated CSV should have M + K data rows.
- Check the database: reconciliation_records table should also have M + K rows.

ISSUE 05 — ANOMALY WORKFLOW BLOCKS REPORT GENERATION WITH NO RESOLUTION PATH
Severity  : HIGH
Files     : src/main/java/aval/service/ReportService.java
            src/main/java/aval/ui/controller/ReportController.java
            src/main/java/aval/ui/controller/ReconController.java
================================================================================

PROBLEM
-------
ReportService.generateReconciliationReport() has this contract:
"Throws UnresolvedItemsException if pendingHypotheses or unresolvedAnomalies
are non-empty."

AnomalyDetectionEngine.identifyAnomalies() flags:
- Exact duplicate transactions (same date + amount)
- Outliers > 3 standard deviations
- Sunday-dated transactions

All three are common in real financial datasets. When anomalies are detected,
they are stored in MainUIContext.anomalies as List<String>. In
ReportController.handleGenerate(), those strings are passed directly to
generateReconciliationReport() as the unresolvedAnomalies parameter.

Result: If any anomaly was detected at all, calling generateReconciliationReport()
throws UnresolvedItemsException and the report cannot be generated. There is no
screen in the UI for the user to review or dismiss anomalies. Report generation
is permanently blocked.

FIX — Two parts: UI anomaly review panel + correct report call
-------------------------------------------------------------

PART A: Add anomaly review to the ManualCheck screen.
The Manual Check screen is the natural place to review anomalies alongside
low-confidence hypotheses.

In ManualCheck.fxml, add a collapsible anomaly section below the hypothesis table:

    <!-- Anomaly Review Panel -->
    <VBox fx:id="anomalyPane" spacing="8" style="-fx-padding: 0 0 20 0;"
          visible="false" managed="false">
        <Label text="Detected Anomalies" styleClass="section-heading" />
        <Label text="Review and dismiss each flagged item to enable report generation."
               styleClass="mc-sub" wrapText="true" />
        <ListView fx:id="anomalyList" prefHeight="180" styleClass="data-table" />
        <Button text="Dismiss All Anomalies" onAction="#handleDismissAnomalies"
                styleClass="btn-ghost" />
    </VBox>

In ManualCheckController, add:

    @FXML private VBox anomalyPane;
    @FXML private ListView<String> anomalyList;

    private boolean anomaliesDismissed = false;

    // Call this from WorkspaceController.showManual() after setItems()
    public void loadAnomalies() {
        List<String> anomalies = MainUIContext.getInstance().getAnomalies();
        if (anomalies != null && !anomalies.isEmpty()) {
            anomalyList.setItems(FXCollections.observableArrayList(anomalies));
            anomalyPane.setVisible(true);
            anomalyPane.setManaged(true);
        } else {
            anomaliesDismissed = true; // no anomalies = already clear
        }
    }

    @FXML
    void handleDismissAnomalies() {
        anomaliesDismissed = true;
        anomalyPane.setVisible(false);
        anomalyPane.setManaged(false);
        // Clear anomalies from context so they are not passed to ReportService
        MainUIContext.getInstance().setAnomalies(new ArrayList<>());
        checkIfComplete();
    }

    // Modify checkIfComplete / the footer trigger to require anomalies dismissed:
    private void checkIfComplete() {
        if (resolved >= mcTable.getItems().size() && anomaliesDismissed) {
            mcCompleteBar.setVisible(true);
            mcCompleteBar.setManaged(true);
        }
    }

PART B: Fix ReportController to pass empty anomaly list (after dismissal).
The context's anomaly list is cleared when the user clicks Dismiss, so:

    List<String> anomalies = ctx.getAnomalies();
    if (anomalies == null) anomalies = new ArrayList<>();
    // After dismissal, this list is empty and ReportService will not throw.

VERIFICATION
------------
- Ingest a dataset that contains duplicate transactions.
- Run reconciliation. Anomalies should appear in the Manual Check screen.
- Before dismissing, click Proceed to Report — it should not be available.
- Dismiss anomalies. Proceed to Report becomes available.
- Generate report — no UnresolvedItemsException.

ISSUE 06 — MAINCUICONTEXT IS NOT THREAD-SAFE
Severity  : HIGH
Files     : src/main/java/aval/ui/MainUIContext.java
================================================================================

PROBLEM
-------
MainUIContext is a singleton accessed by both the JavaFX Application Thread
(reading values to update UI) and multiple background Task threads (writing
values after ingestion, matching, and approval). All fields are plain Java
object references with no visibility guarantees.

The Java Memory Model does not guarantee that a write made on Thread A is
visible to Thread B without a happens-before relationship. In practice this
causes:
- stale reads (UI shows old data after ingestion completes)
- lost writes (one Task's result overwrites another's silently)

The most dangerous races are on:
  - standardizedLedgerTransactions (written by ledger Task, read by recon Task)
  - reconciledRecords (written by multiple ManualCheck Task calls)
  - allHypotheses (written by recon Task, read by Report screen)

FIX — Make fields volatile and list mutations synchronized
---------------------------------------------------------

For simple reference assignments (set once, read later), volatile is enough:

    private volatile SystemUser currentUser;
    private volatile ReconciliationWorkspace activeWorkspace;
    private volatile List<MatchHypothesis> allHypotheses;
    private volatile List<StandardizedTransaction> standardizedLedgerTransactions;
    private volatile List<StandardizedTransaction> standardizedBankTransactions;
    private volatile List<StandardizedTransaction> unmatchedLedger;
    private volatile List<StandardizedTransaction> unmatchedBank;
    private volatile List<String> anomalies;
    private volatile List<MatchHypothesis> pendingHypotheses;

For reconciledRecords, which is appended to from multiple threads:

    private final List<ReconciliationRecord> reconciledRecords =
        Collections.synchronizedList(new ArrayList<>());

    public List<ReconciliationRecord> getReconciledRecords() {
        synchronized (reconciledRecords) {
            return new ArrayList<>(reconciledRecords); // return defensive copy
        }
    }

    public void setReconciledRecords(List<ReconciliationRecord> records) {
        synchronized (reconciledRecords) {
            reconciledRecords.clear();
            reconciledRecords.addAll(records);
        }
    }

    public void addReconciledRecord(ReconciliationRecord record) {
        reconciledRecords.add(record); // synchronizedList handles this
    }

VERIFICATION
------------
Run the ingestion for ledger and bank files with short pauses between starting
each, so Tasks genuinely overlap. Confirm that both datasets are available in
context after both Tasks complete. No NPE or stale-data symptoms should appear.

ISSUE 07 — WORKSPACE STATUS NEVER UPDATED ON EXIT
Severity  : HIGH
Files     : src/main/java/aval/ui/controller/WorkspaceController.java
================================================================================

PROBLEM
-------
WorkspaceController.handleExit() does this:

    MainUIContext.getInstance().setActiveClient(null);
    // ... navigates to Registry.fxml

It never calls dataStore.updateWorkspaceStatus(workspaceId, COMPLETED).
Every reconciliation_workspace row created during a session stays permanently
in IN_PROGRESS status. Any future query filtering by status (e.g., history
dashboard, reporting across periods) returns wrong results.

FIX — Call updateWorkspaceStatus before navigating away
-------------------------------------------------------

    @FXML
    void handleExit() {
        ReconciliationWorkspace workspace =
            MainUIContext.getInstance().getActiveWorkspace();
        DataStore ds = MainUIContext.getInstance().getDataStore();

        if (workspace != null && ds != null) {
            Task<Void> closeTask = new Task<>() {
                @Override protected Void call() throws Exception {
                    ds.updateWorkspaceStatus(
                        workspace.getWorkspaceId(),
                        WorkspaceStatus.COMPLETED
                    );
                    return null;
                }
            };
            // Fire and forget — don't wait, just initiate
            new Thread(closeTask).start();
        }

        // Clear session state
        MainUIContext ctx = MainUIContext.getInstance();
        ctx.setActiveClient(null);
        ctx.setActiveWorkspace(null);
        ctx.setAllHypotheses(null);
        ctx.setStandardizedLedgerTransactions(null);
        ctx.setStandardizedBankTransactions(null);
        ctx.setUnmatchedLedger(null);
        ctx.setUnmatchedBank(null);
        ctx.setAnomalies(null);
        ctx.setPendingHypotheses(null);
        ctx.setReconciledRecords(new ArrayList<>());

        navigateTo("Registry.fxml");
    }

Note: The context clearing block also fixes Issue 10 (stale MainUIContext state).

VERIFICATION
------------
Enter and exit a workspace. Check the database:
    SELECT * FROM reconciliation_workspace;
The row's status column should read 'COMPLETED'.

ISSUE 08 — HARDCODED DATABASE CREDENTIALS AND ENDPOINTS IN MAIN.JAVA
Severity  : HIGH
Files     : src/main/java/aval/Main.java
================================================================================

PROBLEM
-------
Main.java contains:

    String url  = "jdbc:postgresql://localhost:5432/aval_db";
    String user = "aval_user";
    String pass = "aval_password";
    // and:
    new LangChain4jVectorizationEngine("http://localhost:11434", "nomic-embed-text");

These are hardcoded string literals. There is no way to change the database host,
port, credentials, or Ollama endpoint without recompiling the application.
In any environment other than a developer's local machine (staging, client
deployment), this will either fail to connect or expose credentials in source
control.

FIX — Load configuration from a properties file
----------------------------------------------

Step 1. Create src/main/resources/aval.properties:

    # Database
    db.url=jdbc:postgresql://localhost:5432/aval_db
    db.username=aval_user
    db.password=aval_password
    db.pool.maxSize=10

    # Ollama / Vectorization
    ollama.baseUrl=http://localhost:11434
    ollama.model=nomic-embed-text

Step 2. Add aval.properties to .gitignore so it is never committed:

    # In .gitignore:
    src/main/resources/aval.properties

Step 3. Provide a safe template file at src/main/resources/aval.properties.template:

    db.url=jdbc:postgresql://HOST:5432/aval_db
    db.username=CHANGE_ME
    db.password=CHANGE_ME
    db.pool.maxSize=10
    ollama.baseUrl=http://localhost:11434
    ollama.model=nomic-embed-text

Step 4. Load the properties file in Main.java:

    private static Properties loadConfig() throws IOException {
        Properties props = new Properties();
        // First try the classpath (src/main/resources/aval.properties)
        InputStream classpathStream =
            Main.class.getResourceAsStream("/aval.properties");
        if (classpathStream != null) {
            props.load(classpathStream);
            return props;
        }
        // Fallback: look next to the JAR
        File externalFile = new File("aval.properties");
        if (externalFile.exists()) {
            props.load(new FileInputStream(externalFile));
            return props;
        }
        throw new IOException(
            "aval.properties not found. Copy aval.properties.template " +
            "to aval.properties and fill in your values.");
    }

Step 5. Use the properties in Main.start():

    Properties config = loadConfig();

    HikariConfig hikariConfig = new HikariConfig();
    hikariConfig.setJdbcUrl(config.getProperty("db.url"));
    hikariConfig.setUsername(config.getProperty("db.username"));
    hikariConfig.setPassword(config.getProperty("db.password"));
    hikariConfig.setMaximumPoolSize(
        Integer.parseInt(config.getProperty("db.pool.maxSize", "10")));

    VectorizationEngine vecEngine = new LangChain4jVectorizationEngine(
        config.getProperty("ollama.baseUrl"),
        config.getProperty("ollama.model")
    );

VERIFICATION
------------
Change the db.url in aval.properties to point to a wrong port. The app should
fail with a clear "cannot connect" error, not a NullPointerException.
Restore the correct URL. App should start normally.

ISSUE 10 — STALE MAINCUICONTEXT STATE BETWEEN WORKSPACE SESSIONS
Severity  : HIGH
Files     : src/main/java/aval/ui/controller/WorkspaceController.java
            src/main/java/aval/ui/MainUIContext.java
================================================================================

PROBLEM
-------
MainUIContext is a JVM-scoped singleton. When a user exits Workspace A and
enters Workspace B in the same app session, the previous session's data remains:
- standardizedLedgerTransactions from Company A's ledger
- allHypotheses from Company A's reconciliation
- reconciledRecords from Company A's manual review

WorkspaceController.initialize() for Company B reads these stale values.
ManualCheckController.setItems() is called with Company A's pending hypotheses.
ReportController.populateReport() is called with Company A's hypothesis list.

Step 1. Add to DataStore.java:

    public static class ReconciliationHistoryRow {
        public String date, period, txns, matched, rate, anomalies, status;
        public ReconciliationHistoryRow(String date, String period,
            String txns, String matched, String rate,
            String anomalies, String status) {
            this.date=date; this.period=period; this.txns=txns;
            this.matched=matched; this.rate=rate;
            this.anomalies=anomalies; this.status=status;
        }
    }

    public List<ReconciliationHistoryRow> getReconciliationHistoryForOrg(UUID orgId) {
        List<ReconciliationHistoryRow> rows = new ArrayList<>();
        String sql =
            "SELECT " +
            "  DATE(rr.reconciled_at) AS rec_date, " +
            "  rw.workspace_id, " +
            "  COUNT(mh.hypothesis_id) AS total_hyp, " +
            "  COUNT(CASE WHEN mh.status IN ('AUTO_RECONCILED','APPROVED') " +
            "    THEN 1 END) AS matched_hyp, " +
            "  ROUND(100.0 * COUNT(CASE WHEN mh.status IN " +
            "    ('AUTO_RECONCILED','APPROVED') THEN 1 END) " +
            "    / NULLIF(COUNT(mh.hypothesis_id),0), 1) AS rate, " +
            "  rw.status " +
            "FROM reconciliation_workspace rw " +
            "JOIN match_hypotheses mh ON mh.ledger_id IN ( " +
            "  SELECT transaction_id FROM standardized_ledger " +
            "  WHERE source_dataset_id IN ( " +
            "    SELECT dataset_id FROM financial_dataset " +
            "    WHERE workspace_id = rw.workspace_id)) " +
            "JOIN reconciliation_records rr " +
            "  ON rr.hypothesis_id = mh.hypothesis_id " +
            "WHERE rw.org_id = ? " +
            "GROUP BY rec_date, rw.workspace_id, rw.status " +
            "ORDER BY rec_date DESC " +
            "LIMIT 10";

        try (Connection conn = dataSource.getConnection();
             PreparedStatement ps = conn.prepareStatement(sql)) {
            ps.setObject(1, orgId);
            try (ResultSet rs = ps.executeQuery()) {
                while (rs.next()) {
                    long total   = rs.getLong("total_hyp");
                    long matched = rs.getLong("matched_hyp");
                    String rate  = rs.getString("rate") + "%";
                    long anomN   = total - matched;
                    rows.add(new ReconciliationHistoryRow(
                        rs.getString("rec_date"),
                        rs.getString("rec_date").substring(0, 7), // YYYY-MM
                        String.valueOf(total),
                        String.valueOf(matched),
                        rate,
                        String.valueOf(anomN),
                        rs.getString("status")
                    ));
                }
            }
        } catch (SQLException e) {
            System.err.println("getReconciliationHistoryForOrg failed: " + e.getMessage());
        }
        return rows;
    }

    package aval.service;

    import javax.mail.*;
    import javax.mail.internet.*;
    import java.io.File;
    import java.util.Properties;

    public class EmailService {

        private final String host, username, password, fromAddress;
        private final int port;

        public EmailService(String host, int port,
                            String username, String password, String fromAddress) {
            this.host = host; this.port = port;
            this.username = username; this.password = password;
            this.fromAddress = fromAddress;
        }

        public void sendReport(String toEmail, String clientName,
                               File reportFile) throws MessagingException {
            Properties props = new Properties();
            props.put("mail.smtp.auth", "true");
            props.put("mail.smtp.starttls.enable", "true");
            props.put("mail.smtp.host", host);
            props.put("mail.smtp.port", String.valueOf(port));

            Session session = Session.getInstance(props, new Authenticator() {
                @Override protected PasswordAuthentication getPasswordAuthentication() {
                    return new PasswordAuthentication(username, password);
                }
            });

            Message message = new MimeMessage(session);
            message.setFrom(new InternetAddress(fromAddress));
            message.setRecipients(Message.RecipientType.TO,
                InternetAddress.parse(toEmail));
            message.setSubject("AVAL AIRE — Reconciliation Report: " + clientName);

            MimeBodyPart textPart = new MimeBodyPart();
            textPart.setText("Please find the reconciliation report attached.");

            MimeBodyPart filePart = new MimeBodyPart();
            filePart.attachFile(reportFile);

            Multipart multipart = new MimeMultipart();
            multipart.addBodyPart(textPart);
            multipart.addBodyPart(filePart);
            message.setContent(multipart);

            Transport.send(message);
        }
    }
